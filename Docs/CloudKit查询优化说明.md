# CloudKit 查询优化说明

## 📋 问题背景

CloudKit 的 Location 字段查询有一些限制：

1. **不支持直接的距离查询**：CloudKit 不提供类似 `distanceToLocation:fromLocation:` 的查询语法
2. **边界框查询有限**：虽然可以查询，但语法复杂且可能不够精确

## 🔧 解决方案

我们采用**两阶段查询**策略：

### 阶段 1：从 CloudKit 拉取数据
- 查询所有 `isActive == YES` 的公共目的地
- 限制结果数量为 500 条（避免一次拉太多）
- 不进行位置过滤（在 CloudKit 层面）

### 阶段 2：在内存中过滤位置
- 将 CloudKit 返回的所有记录转换为 `PublicDestination`
- 在内存中根据地图可见区域进行边界框过滤
- 只保留在可见区域内的目的地

## ✅ 优点

1. **简单可靠**：不依赖 CloudKit 的复杂查询语法
2. **性能可控**：限制查询数量，避免超时
3. **精确过滤**：内存过滤可以精确控制边界框

## ⚠️ 注意事项

1. **数据量限制**：如果全球有超过 500 个共享地点，可能需要：
   - 增加 `resultsLimit`（但要注意性能）
   - 实现分页加载
   - 按年份或其他维度进一步过滤

2. **性能考虑**：
   - 当前实现适合中小规模数据（< 1000 条）
   - 如果数据量很大，考虑添加更多过滤条件（如年份、国家等）

3. **未来优化方向**：
   - 如果 CloudKit 支持更好的位置查询，可以迁移
   - 考虑使用 CloudKit 的 `CKLocation` 和 `CKQuery` 的其他特性
   - 实现更智能的缓存和预加载策略

## 🔄 替代方案（如果数据量很大）

如果未来数据量增长，可以考虑：

1. **按国家/地区分片**：先查询国家，再查询该国家内的地点
2. **按年份分片**：只查询最近几年的共享地点
3. **使用 CloudKit 的 Reference**：建立地点到区域的引用关系
4. **自定义后端**：如果 CloudKit 限制太多，考虑迁移到自定义后端

---

**当前实现适用于 MVP 和中小规模数据，后续可根据实际使用情况优化。**
