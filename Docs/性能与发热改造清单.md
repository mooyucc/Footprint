# 性能与发热改造清单

> 记录 Footprint App 使用中 CPU 高、Energy Very High、设备发热等问题的根因分析与分阶段改造计划。  
> 设计原则：**像信息流 App 一样——「只处理眼前可见的、离屏即停、基线尽量低」**  
> 创建日期：2026-07-09  
> 关联文档：[旅程线路优化方案.md](./旅程线路优化方案.md)（旅程线路 Sheet 专项）  
> 目标平台：iOS 18+（iOS 26 特性按需 `if #available`）

---

## 一、背景与现象

Xcode Debug Navigator 典型表现：

| 指标 | 典型值 | 说明 |
|------|--------|------|
| CPU | 80～125% | 多核持续高负载 |
| Energy Impact | Very High | CPU + GPU + GPS 叠加 |
| FPS | 30 | 负载高时系统降帧 |
| Network / Disk | 0 | 非联网算路或磁盘 I/O 阶段 |
| Memory | ~400～500 MB | 地图 + 路线 polyline + SwiftData |

**结论**：主要是 **地图渲染 + 主线程频繁刷新 + 持续定位** 导致基线功耗过高，而非「数据量比小红书多」本身。

---

## 二、设计原则对照表

| 原则（借鉴信息流） | Footprint 现状问题 | 改造方向 | 实施状态 |
|-------------------|---------------------|----------|----------|
| 只渲染可见 cell | Map 是整块画布，标注/polyline 全层叠加 | **按 visible region + zoom 分级** 加载/渲染 | ✅ P1-2 / P2-1 |
| 滑走就销毁 | Tab 切走后 `MapView` 仍挂载 | **非地图 Tab 卸载 Map** | ✅ P0-2 |
| 静止就 idle | `onMapCameraChange(.continuous)` 每帧写 `@State` | **手势结束才更新 region** | ✅ P0-1 |
| 离屏暂停 | GPS 导航级精度常开 | **分级精度 + 场景切换** | ✅ P0-3 |
| 缩略图 → 大图 | 路线双 polyline、低 zoom 也画全量折线 | **LOD（Level of Detail）** | ✅ P2-1 |
| 发热降级 | 无 thermal 感知 | **系统 thermalState 降载** | ✅ P3-1 |

## 四、P0 — 立竿见影（必做）

### P0-1 修复地图相机「每帧刷新 SwiftUI」

**状态**：✅ 已实施（2026-07-09）— `MapRegionHolder` + `commitVisibleRegionUpdate()`；`.onEnd` 分频仍可选优化

**问题**  
`pendingRegion = context.region` 在 `.continuous` 回调里每帧写 `@State`，导致整个 `MapView`（6000+ 行）反复求值。防抖只保护了 `visibleRegion` 和 DB fetch，**没有阻止每帧 state 更新**。

**文件**  
- `Footprint/Helpers/MapRegionHolder.swift`（新增）
- `Footprint/Views/MapView.swift`（相机 debounce、`commitVisibleRegionUpdate`）

**改造**  
1. 新增非 Observable 持有者，例如：
   ```swift
   final class MapRegionHolder {
       var pending: MKCoordinateRegion?
   }
   ```
2. `.continuous` 回调里 **只写** `holder.pending`，**不写 `@State`**
3. debounce 300ms 后 **一次性** 写 `visibleRegion`
4. 静止且无动画时，考虑改 `frequency: .onEnd`；`waitingForMapToReachDestination`（回忆泡泡）可单独用 `.continuous` 短生命周期

**验收**  
- [ ] Instruments → SwiftUI：拖动地图 10s，`MapView` invalidation 次数下降 **>80%**
- [ ] 静止 30s，CPU **< 40%**（中等数据量）
- [ ] 区域 fetch / 聚类触发频率不变（仍 debounce 300ms）

**工时**：0.5 天

### P0-2 非地图 Tab 卸载 MapView（离屏即停）

**状态**：✅ 已实施（2026-07-09）— 方案 A：`selectedTab == 0` 时才挂载 `MapView()`

**问题**  
`ContentView.lazyTabContent` 一旦 `loadedTabs` 包含 0，地图 **永久驻留** Tab 树，切 Tab 仍占 GPU/内存。

**文件**  
`Footprint/ContentView.swift`（约 15、100～115、132～138 行）

**改造**  
```swift
// 方案 A（推荐）：仅当前 Tab 挂载
if selectedTab == 0 { MapView() }

// 方案 B：保留 loadedTabs 但非选中时用 EmptyView + onDisappear 清理
if loadedTabs.contains(0) && selectedTab == 0 { MapView() }
```

配套：
- 切离 Tab 0 时已有 `stopUpdatingLocation()` ✅ 保持
- 切回 Tab 0 时 `refetchVisibleDestinationsIfNeeded()`，不重复冷启动定位逻辑

**验收**  
- [ ] 切到「旅程/勋章/我的」10s 后，CPU 接近系统 idle（**< 15%**）
- [ ] Memory 中 Map 相关占用下降（对比 Debug Navigator）
- [ ] 切回地图 Tab **< 1s** 可交互（允许短暂重建）

**工时**：0.5 天

### P0-3 GPS 分级精度（最大单项省电）

**状态**：✅ 已实施（2026-07-09）— `LocationTrackingMode` + `applyMode`；启动屏仅 `requestLocation()`

**问题**  
`kCLLocationAccuracyBestForNavigation` + `distanceFilter = 5m` 对「看地图」过重；启动时 `FootprintApp` 也会提前 `startUpdatingLocation()`。

**文件**  
- `Footprint/Helpers/LocationManager.swift`（58～61 行）
- `Footprint/FootprintApp.swift`（164～166 行）
- `Footprint/ContentView.swift`（106～127 行）

**改造**

| 场景 | desiredAccuracy | distanceFilter | 启停 |
|------|-----------------|----------------|------|
| 地图浏览（默认） | `kCLLocationAccuracyNearestTenMeters` 或 `HundredMeters` | 30～50m | 仅 Tab 0 + active |
| 打卡 / 等待定位 | `Best` | 10m | 短生命周期，用完恢复 |
| 轨迹播放（若有） | `BestForNavigation` | 5m | 播放期间 |

新增 API：
```swift
enum LocationTrackingMode { case mapBrowsing, checkIn, navigation }
func applyMode(_ mode: LocationTrackingMode)
```

启动画面：`requestLocation()` 一次性即可，**不必** `startUpdatingLocation()` 直到进入地图 Tab。

**验收**  
- [ ] Energy Log：地图静止 5min，Energy 从 Very High → **Low～Medium**
- [ ] 控制台静止时 **不再** 频繁打印 `📍 获取到用户位置`
- [ ] 打卡定位精度仍可接受（< 50m）

**工时**：1 天

### P0-4 聚类：computed property 去副作用

**状态**：✅ 已实施（2026-07-09）— `clusterAnnotations` 只读缓存 + `scheduleClusterRecalculationIfNeeded()`（`.utility`）

**问题**  
`clusterAnnotations` 在 body 求值时启动 `Task.detached(.userInitiated)`，易形成「渲染 → 聚类 → @State → 再渲染」循环。

**文件**  
`Footprint/Views/MapView.swift`（3422～3507 行）

**改造**  
1. `clusterAnnotations` **只读** `cachedClusterAnnotations`
2. 新增 `scheduleClusterRecalculationIfNeeded()`，由以下触发：
   - `visibleRegion` 变化（debounce 后）
   - `currentZoomLevelEnum` 变化（已有 `onChange` → `clearClusterCache`）
   - `destinationsInVisibleRegion` 更新
3. Task 优先级改为 `.utility`
4. 相同 `visibleRegionKey` 不重复调度

**验收**  
- [ ] 静止地图不再打印 `🔄 聚合计算完成`
- [ ] 缩放/平移结束后 **最多 1 次** 聚类
- [ ] Time Profiler 中 `MapClusterEngine.clusterGroups` 总时长下降

**工时**：1 天

## 五、P1 — 按需加载与元数据治理

### P1-1 `refreshDestinationMetadata` 去全量扫描

**状态**：✅ 已实施（2026-07-09）— 全量签名已移 `Task.detached`；通知触发 **2s debounce**；**轻量签名** `fetchLightSignature`（count + latest visitDate）✅

**问题**  
`fetchMapChangeSignature` 主线程 fetch **全部** `TravelDestination` 再 hash。

**文件**  
- `Footprint/Helpers/MapDestinationFetcher.swift`（17～22 行）
- `Footprint/Views/MapView.swift`（451～489 行）

**改造**  
1. **优先事件驱动**：已有 `.destinationDeleted` / `.destinationUpdated` 通知 → 增量更新 count/signature，不全量扫
2. 必须全量时：移到 `Task.detached` + debounce **2s** 合并
3. 签名可改为 `fetchCount` + `lastModified` 字段（若模型可加版本号更优）
4. 触发 whitelist：`onAppear`（一次）、通知、用户主动刷新；**禁止** 与 camera 回调联动

**验收**  
- [ ] 地点 500+ 时，打开地图 Tab 主线程卡顿 **< 100ms**
- [ ] Time Profiler 无 `fetchMapChangeSignature` 热点

**工时**：1 天

## 十一、不建议做 / 低优先级

| 方向 | 原因 |
|------|------|
| 去掉 `RouteManager` 持久化 | 会退回每次联网算路 |

| 为省电默认关 MapKit | 核心体验受损 |
