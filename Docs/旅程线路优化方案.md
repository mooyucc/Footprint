# 旅程线路优化方案

> 记录「旅程卡片 → 打开线路地图」场景的卡顿问题、现状分析与优化计划。  
> 创建日期：2026-07-09  
> 关联功能：`JourneyCardsStackView` → `JourneyTripRouteMapSheet` → `MapView(autoShowRouteCards: true)`

---

## 一、问题描述

用户从 **旅程卡片 Tab** 点击地图图标，打开全屏 **旅程线路地图** 时，常见体验问题：

1. **地图出现较慢**：Sheet 弹出后，地图缩放、标注渲染有可见延迟
2. **线路「要等一会」才显示**：距离标签（如「22 公里」）较快出现，但沿道路的 **实线** 较晚才渲染
3. **重复打开同一条旅程**，仍感觉像在「重新算一遍」（尽管路线持久化缓存仍存在）

---

## 二、当前实现路径

### 2.1 打开流程

```
JourneyCardsStackView（卡片 onMapTap）
  → sheet: JourneyTripRouteMapSheet(trip)
    → 新建 MapView(
         autoShowRouteCards: true,
         tripsOverride: [trip],
         ...
       )
    → handleViewAppear()
         → refreshDestinationMetadata()      // Phase 2b 新增
         → handleAutoShowRouteCards()
              → zoomToTripDestinations()     // 0.8s 动画
              → showTripConnections = true
              → Task { calculateRoutesForTrip(incremental: true) }
              → 延迟 0.5s → showRouteCards = true
```

### 2.2 路线渲染两阶段

| 阶段 | 表现 | 代码位置 |
|------|------|----------|
| **占位** | 直线虚线 + 直线距离标签 | `placeholderRouteContent` |
| **实线** | 沿道路 `MKRoute.polyline` + 真实里程 | `tripConnections` + `RouteDistanceLabel` |

因此用户会先看到「22 公里」等标签，实线随后才替换占位线——**这是当前设计，不是 Bug**。

### 2.3 相关核心文件

| 文件 | 职责 |
|------|------|
| `Footprint/Views/JourneyCardsStackView.swift` | 卡片 → Sheet 入口 |
| `Footprint/Views/MapView.swift` | 线路地图、`handleAutoShowRouteCards`、`calculateRoutesForTrip` |
| `Footprint/Helpers/RouteManager.swift` | 段级路线缓存（内存 + 磁盘） |
| `Footprint/Helpers/TripRoutePrecomputationStore.swift` | 主地图 `tripRoutes` → 卡片里程同步 |
| `Footprint/Views/MapComponents/MapRouteComponents.swift` | 路线卡片 `RouteCard`、预计算路线展示 |

## 三、已有能力（无需重复建设）

### 3.1 RouteManager 段级持久化缓存 ✅ 仍在

- **磁盘路径**：`Application Support/RouteCache/routes.json`
- **有效期**：30 天
- **Key**：`起点 lat,lon → 终点 lat,lon | 交通方式`
- **内容**：距离、耗时、完整 polyline 折线坐标

### 3.2 增量计算 ✅ 仍在

`calculateRoutesForTrip(..., incremental: true)` 会对每一段调用 `RouteManager.getCachedRoute`：

- 全部命中 → 控制台输出：`✅ 旅程 xxxxxxxx 的路线全部来自缓存`
- 部分命中 → 仅对未缓存段发起 `MKDirections`
- 全部未命中 → 并发请求（最多 5 路，`100ms` 节流）

### 3.3 TripRoutePrecomputationStore ✅ 仍在

主 Tab 地图算完路线后 `sync(from: tripRoutes)`，供旅程卡片总里程与 `RouteCard` 使用。

**局限**：打开 Sheet 时 **不会** 从 Store 预填新 MapView 的 `tripRoutes`（单向同步）。

## 四、卡顿根因分析

| 根因 | 说明 | 与近期优化的关系 |
|------|------|------------------|
| **每次新建 MapView** | Sheet 内 `tripRoutes` 内存状态从空开始 | Tab 懒加载、去 `@Query` 不直接影响此路径 |
| **UI 时序** | 先 `showTripConnections`，后异步填 `tripRoutes` → 必先显示占位线 | 无 |
| **MKDirections 网络** | 首次打开 / 缓存 miss / 部分 miss 时需请求 Apple 路线 API | 无 |
| **地图缩放动画** | `zoomToTripDestinations` 固定约 **0.8s** | 无 |
| **卡片延迟** | `showRouteCards` 额外 **0.5s** | 无 |
| **无关 metadata 刷新** | `handleViewAppear` 调用 `refreshDestinationMetadata()` 全量扫描地点签名 | **Phase 2b 可能加重 Sheet 打开耗时** |
| **线路模式仍跑聚类** | `clusterMarkers` 与 `tripConnections` 同时存在 | Phase 2a 聚类已移后台，但仍消耗资源 |
| **缓存粒度** | 按「相邻两点段」缓存，无「整趟旅程签名」一键 restore | 产品语义与实现不完全一致 |

## 五、优化计划

### 第一档：高收益、改动小（建议优先实施）✅ 已实现（2026-07-09）

#### 5.1 打开 Sheet 时预填 `tripRoutes` ✅

**实现**：`MapView.prefillTripRoutesFromCache` + `RouteManager.cachedRoutes(for:)` + `TripRoutePrecomputationStore.precomputedRoutes`

#### 5.2 缓存全命中时跳过占位线 ✅

**实现**：`presentTripRoute` 先预填 `tripRoutes`，再 `showTripConnections = true`；全命中时不启动 `calculateRoutesForTrip` Task

#### 5.3 线路模式跳过 `refreshDestinationMetadata()` ✅

**实现**：`handleViewAppear` 中 `if !autoShowRouteCards { ... }`

#### 5.4 缓存命中时缩短动画 ✅

**实现**：全命中时 `zoomToTripDestinations` 使用 **0.25s**，`showRouteCards` 延迟 **0.05s**（否则 0.8s / 0.5s）

**共用方法**：`presentTripRoute(tripId:destinations:)` — `handleAutoShowRouteCards`、`handleCardAppear` 均调用

---

### 第二档：中等改动

#### 5.5 线路模式简化地图层 ✅（部分）

`autoShowRouteCards == true` 时：

- [x] 使用 `routeTripDestinationMarkers` 替代 `clusterMarkers`（跳过聚类计算）
- [x] 确认不触发天气请求（已有 `guard !autoShowRouteCards`）
- [ ] 评估是否隐藏与线路无关的浮动控件

---

#### 5.6 旅程卡片页后台预热

在 `JourneyCardsStackView` 中，对当前可见 1～3 张卡片：

- [ ] 后台 `calculateRoutesForTrip(incremental: true)`（仅补 miss）
- [ ] 结果写入 `TripRoutePrecomputationStore`

**注意**：控制并发，避免同时预热多条旅程触发 `MKDirections` 限流。

---

#### 5.7 优化 Sheet 打开时序

- [ ] 考虑在 `JourneyTripRouteMapSheet.onAppear` 先预填路线，再展示 Map
- [ ] 或 MapView 增加 `prefilledTripRoutes: [UUID: [MKRoute?]]` 初始化参数

---

### 第三档：架构级（可选，数据量/重复打开进一步增大时）

#### 5.8 旅程级「路线包」缓存

在段缓存之上增加：

```text
tripId + destinationsSignature + transportPreferencesSignature
  → 整趟 [MKRoute?] 快照（磁盘）
```

- 签名不变 → O(1) 整包 restore
- 增删改一个点 → 只 invalidate 受影响段

更符合「线路没变就直接用」的产品语义。

---

#### 5.9 Sheet 内 MapView 实例复用（可选）

同一会话内复用线路 Map 容器，只切换 `trip`，保留 `tripRoutes` 内存。改动面大，收益限于同 session 反复打开。

## 六、不建议优先做的方向

| 方向 | 原因 |
|------|------|
| 去掉 `RouteManager` 持久化 | 会退回每次联网算路 |
| 提高 MKDirections 并发超过 5 | Apple 建议上限，已有 semaphore |
| 为线路 Sheet 恢复 Map 全量 `@Query destinations` | 与 Phase 2b 方向相反，对线路无帮助 |
| 仅用直线距离代替 MKRoute | 已有占位线，不应作为终态方案 |

---

## 七、实施顺序建议

```text
Step 1（1～2 天）
  ├── 5.1 打开前预填 tripRoutes
  ├── 5.2 全命中跳过占位线
  ├── 5.3 线路模式跳过 refreshDestinationMetadata
  └── 5.4 缓存命中时缩短动画

Step 2（2～3 天）
  ├── 5.5 线路模式禁用聚类
  └── 5.6 卡片页后台预热

Step 3（可选）
  └── 5.8 旅程级路线包 + 签名 invalidation
```

## 八、验收标准

同一条、**未改过地点/顺序/坐标** 的旅程，**第二次**打开线路地图：

| 指标 | 目标 |
|------|------|
| 控制台 | 出现 `✅ 旅程 xxxxxxxx 的路线全部来自缓存` |
| 实线出现 | < 300ms，几乎看不到占位虚线 |
| 地图可交互 | 打开后 1s 内可缩放、拖动 |
| 首次打开 | 允许占位线 + 渐进变实线，但不应长时间全屏空等 |

**测试矩阵**：

- [ ] 2 个地点的短旅程
- [ ] 10+ 地点、跨城区旅程（如上海）
- [ ] 多日筛选（「第几天」下拉）
- [ ] 修改一个地点坐标后重新打开（应触发部分/全部重算）
- [ ] 切换某段交通方式后重新打开
- [ ] 冷启动后第二次打开（验证磁盘缓存）

## 九、调试方法

1. **Xcode 控制台** 过滤关键字：
   - `路线全部来自缓存`
   - `路线计算完成`
   - `聚合计算完成`（线路模式 ideally 不应频繁出现）

2. **Instruments → Time Profiler**  
   复现路径：旅程卡片 → 点地图图标 → 等待实线出现  
   关注：`calculateRoutesForTrip`、`MKDirections`、`refreshDestinationMetadata`、`clusterAnnotations`

3. **对比首次 vs 第二次打开**  
   同一旅程连续打开两次，对比实线出现时间与控制台日志。

## 十、与近期性能优化的关系

| 已做优化（Phase 1 / 2a / 2b） | 对旅程线路 Sheet 的影响 |
|------------------------------|------------------------|
| Tab 懒加载 | 无直接关系（Sheet 独立） |
| Profile / Badge 后台化 | 无 |
| 聚类移出主线程（2a） | 略好，但线路模式仍触发聚类 |
| Map 去全量 `@Query`（2b） | 线路用 `trip.destinations`；但 `refreshDestinationMetadata` 可能增加 Sheet 打开开销 |

**结论**：旅程线路卡顿需 **单独优化**（本文档 Step 1），不能指望足迹地图 Tab 的优化自动解决。
